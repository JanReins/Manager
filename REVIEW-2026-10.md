## 2. Already done well

- **Offline policy holds**: no network permission, client, telemetry or crash SDK; CI fails the build if a network permission appears.
- **Crypto basics are right**: PBKDF2-HMAC-SHA256, 32-byte random salt, 256-bit key; AES-256-GCM with a fresh random 96-bit nonce per encryption and 128-bit tag; no nonce-reuse path.
- **Biometric binding**: Keystore AES key with per-use auth (`setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)` / validity −1 pre-R), `setInvalidatedByBiometricEnrollment(true)`, BIOMETRIC_STRONG only, unwrap only via the authenticated `CryptoObject`, unwrapped bytes zeroed, unwrapped key checked against the verifier.
- **Portable backup v2**: magic + version + bounded work factor + salt + IV, whole header as GCM AAD, 600k iterations, 12-char minimum, size caps, all-or-nothing validated import into the destination key, legacy import explicit.
- **Crash-safe password change**: pending salt/verifier journal committed before the single Room batch, promotion inside the same mutation gate, recovery on next password unlock.
- **Session**: starts locked after process death, generation counter stops late auth from reopening a locked session, lock clears decrypted lists/search/generated password; `FLAG_SECURE` set before content (Compose dialogs/sheets inherit it).
- **Leak controls**: `allowBackup=false` + full exclusion in both `backup_rules` and `data_extraction_rules`; no `Log.*`/`println`/`printStackTrace`; no `rememberSaveable`/`SavedStateHandle` holding secrets; Android 13+ clipboard sensitive flag; no secrets or keystores in git history.
- **Generator**: `SecureRandom.nextInt(bound)` (no modulo bias) and the same RNG for shuffle.
- **TOTP**: RFC 4226/6238 truncation, SHA1/256/512, 6–8 digits, 15–120 s period, strict RFC 4648 validation in the editor (padding, case, whitespace, unused bits), locale-safe formatting, RFC vectors in tests.

### Details and fixes

**F-01 (High) — picker suppression defeats background lock.** `suppressNextBackgroundLock()` arms a one-shot flag that skips the next `onStop`. Scenario: auto-lock = "Immediately when app is backgrounded" (`timeoutMillis = 0` disables the inactivity loop at `VaultViewModel.kt:164`), open Export/Restore, press Home from the picker. VaultLock's only `onStop` was consumed, so it stays unlocked in the background until the process dies; reopening from Recents shows the vault. With the default 120 s the exposure is bounded by the inactivity timer. A picker-launch exception (`SettingsScreen.kt:368-371`, `446-450`) also leaves the flag armed for the next Home press. *Fix (bounded, fixes F-08 too)*: delete the suppression flag and always lock on a real stop. Hold the already-encrypted export bytes in the ViewModel and write them in the `CreateDocument` result even while locked (ciphertext only). For import, keep the picked bytes in the ViewModel and show the backup-password dialog after unlock. Register both launchers outside the unlocked-only NavHost branch. Tests: Robolectric for "stop while picker open locks", "export completes while locked", "import waits for unlock".

**F-02 (Med; Codex rated High) — recovery trusts one row.** `keyDecryptsVault` strict-decrypts only `firstOrNull()`. If a pending journal exists and that row is corrupt, the correct NEW password yields `pendingKey` but the probe says `false`, so lines 326-333 clear the journal and tell the user to use the old password; every other row is under the new key whose salt is now gone. The old password path at 334-338 can equally loop forever. Requires a crash mid-change plus a damaged first row, but the result is total loss. *Fix*: probe rows until one decrypts (positive evidence) for either key; clear/promote the journal only on positive evidence; if neither key authenticates any row, keep the journal and surface an error. Add a regression with a corrupt first row.

**F-03 (Med; Codex High) — plaintext v1 titles.** The original schema (`ed09be7`, 2026-08-24) stored `title` in plaintext; `MIGRATION_1_2` (added `93f3f6d`, 2026-08-31) copies it verbatim into `encrypted_title`. After upgrade those rows render "[Decryption Failed]" and strict export/rotation refuse the whole vault; the plaintext title also stays at rest. Only installs that ran a build from 24–31 Aug 2026 are affected (question Q1). *Fix*: in the migration, move legacy titles into a temporary `legacy_plain_title` column (or tag them), and on the first successful unlock encrypt them in one transaction and drop the plaintext. Do not treat arbitrary GCM failures as plaintext. Extend `VaultDatabaseMigrationTest` through a repository read.

**F-04 (Med) — unversioned 150k PBKDF2.** OWASP's current guidance for PBKDF2-HMAC-SHA256 is 600k; backups already use 600k. The iteration count is a constant and not stored with the salt/verifier, so raising it would derive a different key for existing vaults. Mitigation today: salt and verifier sit in Keystore-backed EncryptedSharedPreferences, so offline attack needs the device keystore. *Fix*: store `kdf_iterations` with the current and pending credentials (missing = 150k), derive with the stored value, and use 600k (benchmarked on a low-end device) for new setups and every password change. No forced migration.

**F-05 (Med) — master password visible to the IME.** `PasswordVisualTransformation` only masks rendering; without `KeyboardOptions(keyboardType = KeyboardType.Password)` the IME receives a normal text field, shows suggestions and may add the word to its (possibly synced) dictionary. Unlock/setup and backup dialogs already set it. *Fix*: add `KeyboardType.Password, autoCorrect = false` to the three fields; add a UI test asserting the IME options.

**F-06 (Med) — rotation locks the vault.** `onStop` calls `onAppBackgrounded()` unconditionally; no `configChanges` are declared, so rotation/theme/fold/resize recreate the activity through `onStop`. The vault locks and the Add/Edit form is discarded. *Fix*: `if (!isChangingConfigurations) viewModel.onAppBackgrounded()`. The ViewModel and session survive recreation, which is safe.

**F-07 (Med) — empty generated password after lock.** `clearedForLock()` sets `currentGeneratedPassword = ""` and the unlock branch never regenerates (only the constructor does). After any background/auto-lock, the editor's generator sheet's "Use this Password" overwrites the existing password with "". Save accepts an empty password. *Fix*: regenerate on unlock (or when the generator composes with an empty value), disable Copy/Use while empty, and ignore empty values in `onUsePassword`. Test: lock → unlock → generator value non-empty.

**F-08 (Med) — export payload lost.** See F-01; same fix (ViewModel-held ciphertext, launcher outside the unlocked branch). If bytes are missing when a URI returns, show an explicit failure and delete the empty document (`DocumentsContract.deleteDocument`).

**F-09 (Med) — clipboard clear doesn't survive process death.** Backgrounding deliberately keeps the clip so the user can paste; the 30 s `Handler` dies with the process, and `onCleared` is not called on process death. *Fix (bounded)*: on `onStart`/`onCreate` clear any clip whose label starts with `VaultLock:` (foreground can read it), and add a Settings option "clear clipboard when leaving the app". State in the UI that the 30 s clear is best effort. (A persistent alarm/WorkManager job is the heavier alternative.)

**F-10 (Med, unverified) — IME typing isn't activity.** `onUserInteraction` is driven by key/touch events dispatched to the activity; soft-keyboard commits arrive through `InputConnection`. *Fix*: also call `viewModel.onUserActivity()` from the editor's `onValueChange` handlers (or a `Modifier.onKeyEvent`/text-change hook). Confirm on a device first.

**F-11 (Low; Codex Med) — wall-clock deadlines.** Moving the clock forward ends a lockout early; backward while unlocked extends idle time (backgrounding still locks). Gain is small because the backoff caps at 60 s. *Fix*: compute delays with `SystemClock.elapsedRealtime()` plus the boot count (`Settings.Global.BOOT_COUNT`), fall back to a full backoff after reboot, and `commit()` the failed-attempt counter before showing the result.

**F-12 (Low; Codex Med) — secret lifetime.** `deriveKey` clears only `PBEKeySpec`'s internal clone; the caller's `toCharArray()` copies are never filled. Compose `TextField` forces `String`, so complete zeroing is impossible; the fix is hygiene: fill the arrays in `finally` at each call site, fill `masterKeyToWrap.encoded` after wrapping, and correct the KDoc at `CryptoManager.kt:40` and the class KDoc.

**F-13 (Low; Codex Med) — no AAD on fields.** Needs write access to the app's DB (root/backup tooling), so Low. *Fix (later, format change)*: v2 field envelope with AAD = field name (+ stable row UUID), authenticated empty values, migrated lazily on the next password change. Recommend deferring; listed in out-of-scope.

**F-14 (Low) — clearing someone else's clip.** `description == null` is treated as "still ours". *Fix*: when ownership can't be read, defer the clear to the next foreground (`onStart`) instead of clearing blind; combine with F-09.

**F-15 (Low)** — set `"android.content.extra.IS_SENSITIVE"` in the description extras on all API levels (the constant is only *named* in 33).

**F-16 (Low)** — handle `onAuthenticationFailed` as a hint only (no `onError`); keep `onError` for `onAuthenticationError`. Callers then get exactly one terminal callback.

**F-17 (Low)** — run `EntryValidation.isValidTotpSecret` (and normalisation) on imported `totpSecret` in `validateBackupEntry`; reject the whole import on failure (consistent with all-or-nothing).

**F-18 (Low)** — pass the loaded snapshot (or `updatedAt`) into `saveEntry` and reject if the row changed under the gate. Only worth doing if multi-window/multi-instance is ever enabled.

**F-19 (Low)** — draw all characters uniformly from the combined pool and reject candidates missing a selected class (rejection sampling). Keep existing generator tests passing.

**F-20 (Low)** — for generated values, label strength from computed entropy (pool size × length, or words × 12.9 bits for passphrases) instead of the heuristic; keep the heuristic for typed passwords and add keyboard-run detection inside longer strings. This is the same entropy/label code Phase 2 needs, so do it in the passphrase PR.

**F-21 (Low)** — remove the `<provider>` and `file_paths.xml` (no `getUriForFile` call exists).

**F-22 (Low)** — publish minified release builds once the signing secrets exist (Q4); until then note that debug builds expose preview/test activities (no vault data is reachable through them).

**F-23 (Low)** — fix the TOTP hint text; group 8-digit codes as `1234 5678` (and 7 as `123 4567`).

## 4. Ranked fix plan (PR-sized batches)

Protected: ViewModel session flow. ~150 lines + Robolectric tests.
2. **PR B — Recovery & migration data safety** (F-02, F-03, F-17). Positive-evidence probe for pending recovery; tagged plaintext-title migration + post-unlock encryption; strict TOTP on import. Protected: VaultRepository, VaultDatabase migrations, unlock flow. Depends on Q1.
3. **PR C — Input & clipboard leaks** (F-05, F-09, F-14, F-15). Password keyboard on change-password fields; clear stale `VaultLock:` clips on start; deferred clear when ownership unknown; sensitive flag on all APIs; optional "clear on leave" setting (Q3).
4. **PR D — Generator & editor correctness** (F-07, F-10, F-23, F-16). Regenerate on unlock, disable Use/Copy when empty, IME activity hook, TOTP hint/grouping, biometric failed-attempt handling.
5. **PR E — KDF versioning** (F-04, F-11, F-12). Stored iteration count (600k for new/changed passwords), monotonic lockout + committed counter, password-array zeroing and KDoc fixes. Protected: CryptoManager/SecurityPreferences. Needs a low-end-device timing check (Q2).
6. **PR F — Passphrase generator (Phase 2, as briefed)**: mode toggle with remembered mode/options, bundled EFF large wordlist (7776 words, CC BY 3.0, attribution in README), 4–10 words, separators, capitalisation, optional digit, `SecureRandom.nextInt(7776)`, entropy-based strength labels shared with password mode (absorbs F-20; F-19 optional here), existing clipboard path, tests incl. injectable test RNG. Independent of A–E; can go first if Jan prefers, but after PR D avoids a conflict in `PasswordGeneratorScreen`/`VaultViewModel` generator state.

Low-value items not in a batch: F-13 (format change), F-18 (theoretical), F-22 (resolved by release signing).
